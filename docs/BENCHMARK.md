# Benchmark Method

The research question is: how does containerized RDF monitoring scale when monitored population and actual ABox grow while ontology, SPARQL catalog, resources, hardware, RDFS semantics, and concurrency remain fixed?

Independent variables are users (`1, 50, 100, 500, 1000, 2000, 4000, 5000, 6000, 7000, 10000, 12000, 14000, 16000, 18000, 20000`) and layout (`distributed`, `replicated`). This studies ABox growth rather than TBox complexity. The 4000--7000 extension follows a fully successful 2000-user physical campaign. The 10000--20000 range uses 2000-user increments after a fully successful 7000-user campaign and intentionally locates the memory, CPU, and deadline frontier with greater resolution. Controlled values are logical concurrency one, one container per host, one CPU, 1536 MiB RAM, the fixed 113-query catalog, 18 complete catalog rounds, one warm-up, three measured repetitions, and seed 2026. One round is one serial execution of the logical catalog. A distributed logical query fans out concurrently to its required physical participants and is merged before the next logical query starts. The 18 rounds retain three complete rotations over six hosts for single-participant routing.

The canonical scenario dataset is generated once and reused byte-for-byte. Dataset generation time is recorded and excluded from preparation. A reference partition is computed only to establish expected fragment and closure digests. Before each scenario-layout combination, all six worker containers are restarted and their semantic contract is verified; `cold-start.json` preserves this evidence. The warm-up therefore starts from a process-level cold baseline and is stored separately from the statistics. Every warm-up and measured repetition then independently resets the RDF graph, partitions, serializes, transfers, parses, loads, reasons, validates, executes the catalog, samples resources, and persists evidence. Measured repetitions intentionally retain the warmed process and system caches established by the warm-up.

The worker exposes `T_parse_digest`, `T_reasoning`, and `T_store_load`. `T_remote_load = T_parse_digest + T_store_load`; reasoning remains separate. The backward-compatible component total is `T_prepare = T_partition + T_serialize + critical_path(T_transfer + T_remote_load)` and excludes reasoning. `T_transfer` is the coordinator-observed `/prepare` duration after subtracting worker-reported parsing/store and reasoning; it is not packet-level VPN telemetry. `T_ready` (`ready_seconds`) is the wall-clock interval from the start of partitioning until all workers have received their fragments, parsed and materialized RDFS, constructed their stores, and passed final semantic readiness with the expected graph and closure digests. Workers prepare concurrently, so `T_ready` measures the critical path rather than summing worker durations.

The 120 s operational target applies to `T_ready`. The 600 s `prepare_hard_timeout_seconds` limits each complete remote `/prepare` request, including upload, parse/digest, RDFS materialization, store construction, and response transfer; it does not bound local partitioning or serialization. A timed-out request records `prepare_stage_at_failure=unknown` unless direct worker evidence identifies a stage. The 256 MiB body ceiling remains independent. `--diagnostic-unlimited` removes only the remote `/prepare` request deadline and marks the run non-comparable.

Physical and logical SPARQL limits are distinct. `physical_query_request_timeout_seconds` bounds one coordinator-to-worker request. `logical_query_timeout_seconds` is one monotonic deadline covering routing, concurrent fan-out, collection, and merge. Every physical request receives at most the remaining logical budget. If a required participant fails or times out, successful partial results and failed/pending hosts are persisted, but no complete logical digest is produced. The first logical timeout aborts the repetition and skips all later queries and rounds. `recovery_timeout_seconds` bounds the idle check. Workers that do not return to `idle=true`, `active_requests=0`, and `queue_depth=0` cause all workers to be restarted and verified; failed recovery aborts the remaining repetitions for that layout and scenario.

Older configuration files containing only `request_timeout_seconds` remain loadable: that value becomes the physical timeout and, unless explicitly supplied, the logical timeout. New scientific campaigns must use the two explicit fields so their timeout contract is visible in the configuration snapshot.

Finite HTTP timeouts are global wall-clock deadlines covering connection, upload, server processing, and response transfer. The control plane recalculates the remaining budget between transport phases. Diagnostic unlimited mode deliberately removes this guarantee only for preparation.

The two layouts execute the same logical catalogue. Distributed set results are deduplicated across Edge authorities, ASK results use logical OR, and the Cloud consent projection preserves the one catalogue aggregate that depends on the growing user ABox. Integration tests compare these routed results with full-graph execution before a physical campaign is accepted.

Docker/cgroup data are sampled with a one-second target interval. Every sample carries one of `reset`, `readiness`, `preparation`, `queries`, or `post_check`; phase-start/end events make the timeline reconstructable. `preparation` is intentionally the external phase and is not mislabeled as RDFS because `/prepare` encapsulates parsing, reasoning, and store construction. Reports retain global metrics and add preparation/query CPU mean, p95, peak and seconds plus memory mean, p95, and peak. Raw timestamps retain the achieved interval. Three repetitions support descriptive medians and observed ranges; they do not justify strong inferential claims.
